# FE-005 — بيئات التطوير والتجربة والإنتاج

## القواعد

- لكل بيئة قاعدة بيانات وحسابات وأسرار مستقلة.
- .env.example قالب بلا أسرار؛ ملفات .env الفعلية لا تدخل Git.
- لا تنشر كلمات السر أو روابط اتصال قاعدة البيانات في Notion أو السجلات.
- NODE_ENV=production يصف طريقة تشغيل Next.js؛ لا يثبت أن قاعدة البيانات إنتاجية.
- لا تستعمل قاعدة محلية تحتوي بيانات مهمة لاختبارات المسح.

## تشغيل محلي في نسخة تجربة مستقلة

1. استعمل نسخة منفصلة من المشروع بلا .env أو .env.local من الإنتاج.
2. استعمل Node.js 22، ثم npm ci --include=dev.
3. انسخ .env.example إلى .env فقط إذا لم يكن .env موجودًا.
4. جهز PostgreSQL محلية بقاعدة مخصصة مثل football_edge_demo.
5. اضبط DATABASE_URL واتصال DATABASE_URL_UNPOOLED لنفس القاعدة المحلية.
6. اضبط ALLOWED_EMAILS لحساب التجربة وBETTER_AUTH_URL لعنوان السيرفر المحلي.
7. ولّد BETTER_AUTH_SECRET مستقلًا بواسطة openssl rand -base64 32.
8. اترك مفاتيح AI وTelegram وAPP_URL فارغة أثناء التجربة.
9. شغّل npm run db:check للتحقق من الاتصال.
10. بعد التحقق من الهدف، شغّل npm run db:push لإنشاء الجداول.
11. شغّل npm run dev، وافتح /login وأنشئ حساب التجربة.

DATABASE_URL وALLOWED_EMAILS مطلوبان للاستعمال.
BETTER_AUTH_SECRET مطلوب في تشغيل production build.
لا تضع بيانات حقيقية في الحساب التجريبي.

## الاختبارات التي تمسح البيانات

npm run test:db-guard يتحقق من الحماية بلا اتصال بقاعدة بيانات.

seed:demo وqa:pipeline يرفضان:
- VERCEL_ENV=production.
- أي عنوان قاعدة بعيد، حتى مع QA_ALLOW_REMOTE_DB=1.
- اسم قاعدة لا ينتهي بـ _test أو _ci أو _demo أو _benchmark.
- اتصالًا مباشرًا يستهدف عنوانًا أو منفذًا أو قاعدة مختلفة.

هذه الشروط تقلل الخطأ؛ اسم القاعدة وحده لا يثبت أنها قابلة للمسح.
الحماية لا تشمل db:push، الذي يمكنه تعديل المخطط؛ تحقق من هدفه منفصلًا.
لا تشغّل سكريبتات المسح على Neon، حتى لو كان الفرع للتجارب.

## Vercel Preview وNeon

1. جهز فرع Neon مستقلًا للتجربة. استخدم بيانات اصطناعية أو فرع schema-only؛ لا تنسخ بيانات المستخدمين دون حاجة.
2. استخرج رابط pooled ورابط direct من فرع التجربة نفسه.
3. في إعدادات Vercel، خصص متغيرات قاعدة التجربة لبيئة Preview فقط، وللفرع المحدد عند الحاجة.
4. راجع القيم الموجودة سابقًا: لا يكفي إضافة متغير إذا كانت باقي الأسرار مشتركة مع Production.
5. ضع ALLOWED_EMAILS لمختبري المشروع وأسرار جلسة وcron مستقلة.
6. اضبط BETTER_AUTH_URL على عنوان Preview المستعمل وسجّل حسابات تجربة مستقلة.
7. اترك AI وTelegram غير مفعّلين في أول تجربة.
8. أنشئ deployment جديدًا بعد تغيير الإعدادات.
9. تحقق من /login، تسجيل الدخول، وقراءة الصفحات دون تشغيل التحليل.
10. احتفظ برابط Preview ونتيجة الاختبار فقط؛ لا تحفظ الأسرار في التقرير.

## تغييرات المخطط والاسترجاع

- db:push يطبق تغييرات المخطط مباشرة؛ راجع التغييرات على فرع تجربة أولًا.
- التطبيق قد يطبق ترقيات إضافية عند أول استعمال لقاعدة البيانات عبر bootstrap.ts.
- قبل التجربة، احتفظ بفرع قاعدة سليم وبمعرّف نسخة التطبيق المتوافقة معه.
- جرّب التغيير في فرع مستقل وتحقق من تسجيل الدخول وقراءة البيانات.
- لاختبار الاسترجاع، أعد توجيه Preview إلى الفرع السليم وإلى نسخة التطبيق السابقة المتوافقة، ثم أعد النشر والتحقق.
- إعادة كود قديم وحدها لا تعكس تغييرات المخطط.
- لا تحذف الفرع التجريبي قبل التحقق من الاسترجاع وحفظ الأدلة.

## دليل الإتمام

- نتائج اختبارات الحماية.
- تشغيل محلي موثق بقاعدة اصطناعية.
- تحقق من عدم تتبع ملفات الأسرار.
- رابط PR وفحوصات CI.
- سجل تجربة Preview والاسترجاع إن تم تنفيذهما.

كتابة هذا الدليل لا تعني أن Preview أو الاسترجاع جرى اختباره بالفعل.
